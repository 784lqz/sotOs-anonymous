# v2.4-2.6 · GTK3 over real Wayland (cairo software / wl_shm, NO EGL) — DECORATED ✅

A real, unmodified **GTK3 3.24** app over the honest compositor — the second real
toolkit after SDL2.  GTK3's wayland backend renders a **decorated** window (the
client-side-decoration titlebar + a cairo content area) through a cairo image
surface backed by a `wl_shm` pool/buffer (no `GtkGLArea` → no EGL/GL).

**MILESTONE (verified): GTK renders a DECORATED window.** `gtk_init OK` → image
auto-detect works (v2.5 mime DB) → the Wayland cursor theme loads (v2.6 · needs the
LucAs `fallocate` fix) → `window shown` → cairo `draw callback` fires → the
compositor reads genuine **412x329 wl_shm commits** (the CSD titlebar grows the
360x240 content), **0 faults**.  Gate: `tools/gtk-gate.sh`; boot: `just run-gtk`.

**v2.4** got an *undecorated* window rendering (9-wall cascade).  **v2.5** fixed
gdk-pixbuf image loading (shared-mime-info DB · see below).  **v2.6** adds the full
CSD: `librsvg` + the Adwaita symbolic icons + the cursor theme + a sotfs.img layout
bump (sysroot 48→64 MiB, image 128→144 MiB), and **THE reusable fix — `fallocate`
in LucAs**: libwayland-cursor sizes its cursor `wl_shm` pool with `posix_fallocate`
(memfd_create then posix_fallocate, no ftruncate); LucAs returned `ENOSYS` for
`fallocate` (syscall 285) → the pool failed → `wl_cursor_theme_load` returned NULL →
the CSD aborted with a `cursor_theme_name` assertion.  Implementing `fallocate`
(size-extend, mirrors ftruncate for a memfd) unblocks the cursor theme — and any
guest using `posix_fallocate`.

It took **9 walls** to get here (see UPDATE notes below + the wayland memory):
dynamic-loader caps (lazy regions / sysroot handles / anon-bss-overlay / binstore
cap), the multi-thread **futex-wake** register-restore, **wl_seat completion**
(wl_data_device_manager + v5 + name), baked **xkb keymap data**, **read-only
MAP_SHARED** file mmap, the **statfs ABI** 8-byte overflow, and the **heavy
arena** routing.  The window is **undecorated** (`gtk_window_set_decorated FALSE`)
for now — GTK's client-side-decoration titlebar needs the **symbolic SVG** button
icons (Adwaita), which require `librsvg` + the icon theme (the next fidelity step;
`librsvg`'s 4-lib closure overflows the current sysroot region, so it waits on a
sotfs.img layout bump).  A bare drawing-area window needs no icons.

## v2.5 GTK-fidelity · image loading (gdk-pixbuf) — FIXED

GTK image loading now works.  **Root cause (was misdiagnosed as "the builtin png
loader isn't registering"):** gdk-pixbuf 2.42 is built with GIO sniffing
(`GDK_PIXBUF_USE_GIO_MIME`, the Alpine default), so auto-detect routes through
`g_content_type_guess()`/xdgmime — which needs the **shared-mime-info DB** at
`/usr/share/mime/mime.cache`.  The sysroot shipped no `share/mime/`, so
`g_content_type_guess()` returned `application/octet-stream` for everything and
*every* `gdk_pixbuf` auto-detect (the GtkImage / GtkIconTheme path) failed with
`GDK_PIXBUF_ERROR_UNKNOWN_TYPE` — png (builtin) **and** bmp/svg (external) alike.
`new_with_type("png")` always worked because it resolves by name, never sniffing.
**Fix:** ship the 352 KB shared-mime-info DB (`share/mime/`, generated by
`update-mime-database`) + the real `loaders.cache` + `libpixbufloader-svg.so`.  Now
png/bmp auto-detect+decode, and svg is *detected* (it only fails at module-load
until `librsvg` is shipped).  `gtkspike` carries a 1x1-PNG regression assertion
(`[gtkspike] PNG auto-detect load OK`), gated by `gtk-gate.sh`.  **No code change,
no layout change.**

`gtkspike.c`: `gtk_init` → `GtkWindow` + `GtkDrawingArea` → a cairo "draw" callback
(`cairo_paint`) → a few GLib-main-loop ticks → quit.  Env makes GTK survive a
desktop-less, dbus-less host: `GSETTINGS_BACKEND=memory`, `NO_AT_BRIDGE=1`,
`XDG_DATA_DIRS=/usr/share`, `FONTCONFIG_FILE`, `GDK_PIXBUF_MODULE_FILE`.

## Status (2026-06-08): loads + connects + threads, then BLOCKED on a threading wall

The spike drove GTK through five walls.  Four are FIXED (a separate commit —
generic dynamic-loader improvements, verified non-regressing via sdlspike/doomwl):

1. lazy-region table 8 → 256 (`state.h`) — one per mapped `.so`; 57-lib closure.
2. sysroot backend handle pool 16 → 128 (`backends_sysroot.c`) — a lazy mmap pins
   one handle per lib; **+ release on sotbox teardown** (the global pool leaked).
3. anon `MAP_FIXED` `.bss`-overlay onto an EAGERLY-mapped (<64 KiB) lib
   (`handlers_mem.c`) — the eager path missed the overlay the lazy path caught.
4. binstore `MAX_ENTRIES` 16 → 32 (`binstore.h`) — room for `gtkspike.bin`.

With those, GTK now: **loads all 57 libs · runs `main()` · CONNECTS to the
compositor over wayland** (`[wayland] connect ... -> OK` — the byte-stream
transport works for GTK's libwayland) · spawns GLib worker pthreads
(`[clone] thread create tid=1, tid=2`).

**The 5th wall (UNFIXED):** a worker thread faults `VMFault faultIP=0x14003902c
rsp=0x0` right after a futex WAIT returns `-EAGAIN` — a thread running libc/pthread
code with a **zero stack pointer**, faulting on a `call` (writes `[rsp-8]` →
`0xfffffffffffffff8`).  Thread *creation* sets `rsp=newsp` correctly
(`threading.c:639`) and futex-wake uses `seL4_Send` (kernel preserves regs), so
the bug is in the **multi-threaded Linux-ABI worker-thread syscall/futex resume
path** — something single-threaded SDL2/doomgeneric never exercised.  Needs a
focused threading arc (the procd-cond/futex gates depend on that path — do not
rush it).

`gtkspike` is an **on-demand** sotShell command (`ORCH_OP_GTKSPIKE`), deliberately
NOT in the auto-demo (it would fault 64× — contained — every boot).  Re-add the
`"gtkspike"` `demo_commands[]` entry once the threading wall is fixed.
